# 테이블 오더

손님은 테이블 QR로 주문하고, 직원은 테이블 현황과 주방 화면에서 처리하는 한 매장용 시스템입니다. 현장 카드·현금 수납을 **기록**하며 실제 결제나 환불을 실행하지 않습니다.

**직원 화면을 모두 꺼도 주문을 받습니다.** 서버와 PostgreSQL에 저장한 뒤 손님에게 주문 번호를 반환합니다. 직원이 다시 로그인하면 미확인 주문과 최신 서빙·취소 상태를 자동으로 불러옵니다.

## 바로 실행

### 개발용

Bun **1.4.0**, Podman **5 이상**을 설치합니다. macOS/Windows에서는 먼저 `podman machine init`(최초 한 번), `podman machine start`로 Linux VM을 실행합니다.

```sh
bun install --frozen-lockfile
bun run setup:dev --demo
bun dev
```

- 관리자: http://localhost:5173/admin/
- 손님: 관리자 **매장 설정 → 테이블 → QR 카드 → 주문 주소**
- 초기 관리자: 아이디 `owner`, 비밀번호는 로컬 `.env`의 `ADMIN_PASSWORD`에 생성됩니다. 고정 공용 비밀번호는 없습니다.
- `--demo`는 예시 메뉴와 빈 테이블 12개만 추가합니다. 주문·매출은 생성하지 않습니다. 완전히 빈 매장은 이 옵션을 빼세요.
- 개발 DB는 `127.0.0.1:55432`, 컨테이너 `table-order-dev-db`, 영속 볼륨 `table-order-dev-data`입니다. 준비 명령을 다시 실행해도 초기화하지 않습니다.

### 실제 서버

Linux + systemd + cgroup v2 + rootful Podman 5 이상이 필요합니다. 검증 환경은 Fedora 43 / Podman 5.8 / ARM64입니다. 4 vCPU·8GB 메모리·SSD를 검증 시작 기준으로 삼고, 실제 매장 데이터로 용량을 확인하세요. 공유 서버에서는 기본 80/443 포트와 `ongi-*` 이름 충돌을 먼저 확인합니다.

Fedora 계열:

```sh
sudo dnf install -y podman git rsync
podman --version
```

Debian/Ubuntu 계열은 `sudo apt-get install podman git rsync` 후 **설치된 Podman의 주 버전이 5 이상인지 확인**합니다. 배포판 기본 패키지가 오래됐다면 지원되는 OS/저장소로 먼저 업그레이드하세요. 설치 프로그램은 버전 미달을 거부합니다. [Podman 공식 설치 안내](https://podman.io/docs/installation).

공개 도메인의 A/AAAA를 서버에 연결하고, TCP 80/443을 허용한 뒤 레포에서 실행합니다. HTTP/3를 쓰면 UDP 443도 허용합니다. [Caddy의 인증서 발급 조건](https://caddyserver.com/docs/automatic-https).

```sh
sudo ./ops setup orders.example.com
sudo cat /opt/ongi/secrets/first-login.txt
```

주소만 바꾸면 이미지 빌드, DB·사진·인증서 볼륨, 임의 비밀번호, DB 마이그레이션, HTTPS 프록시, 부팅 시 실행, 일일 로컬 백업까지 구성합니다. 운영 서버에 Bun을 별도로 설치할 필요는 없습니다. Linux에서 직접 실행하며 macOS 셸에서 `sudo ./ops setup`을 실행하지 않습니다.

설치 후 `https://orders.example.com/admin/`에서 **초기 비밀번호 변경 → 매장명 → 메뉴 → 구역·테이블 → QR 다운로드**를 진행합니다. 영업 전 별도 개발 환경에서 주문·소리·정산 흐름을 연습하세요. 운영 설치에는 데모 주문을 넣지 않습니다.

## 매장에서 쓰는 순서

1. 빈 테이블에서 **손님 받기**. 인원 입력은 선택입니다.
2. 손님이 QR 스캔 → 메뉴 담기 → 주문. 같은 팀의 주문 내역을 함께 봅니다.
3. 직원이 **확인 · 준비할게요** → **음식 나감**. 두 번의 조작입니다.
4. 취소는 수량과 사유 버튼으로, 이동은 빈 테이블 선택으로 처리합니다.
5. 현장 수납 후 **정산하기 → 카드/현금으로 정산 · 퇴석**. 아직 식사 중이면 **정산만 · 식사 중**을 선택합니다.
6. 정리 중 테이블에서 **정리 완료**.

알림 소리는 각 수신 기기에서 벨 버튼을 한 번 눌러 켭니다. 시험 소리가 나며, 브라우저를 새로 열었을 때는 다시 켭니다. 브라우저의 절전·음소거 제한은 웹 앱이 해제할 수 없습니다. 소리 설정과 관계없이 주문은 저장되고 목록에 남습니다.

## 포함 기능

| 화면 | 기능 |
| --- | --- |
| 테이블 현황 | 구역·번호·상태 필터, 인원, 새 주문·미서빙·미정산 합계, 착석·퇴석·정리·이동 |
| 주문·주방 | 자동 수신·복구, 주문 확인, 전체/수량별 서빙, 15초 이내 서빙 되돌리기, 부분 취소·사유, 선택적 조리 수량 관리 |
| 직원 주문 | 메뉴 선택, 임의 항목 추가, 요청사항, 장애 때 받은 종이 주문의 실제 시각·사유 기록 |
| 메뉴 관리 | 사진 업로드, 이름·가격·설명, 품절·노출·순서, 카테고리 CRUD·손님 화면 분류 표시 옵션 |
| 정산·인사이트 | 수납 수단·처리자·내역, 원 기록을 보존하는 정산 정정, 판매·취소·방문·시간대·영업일 집계, 내역 페이지 이동 |
| QR 카드 | 매장·테이블·안내 문구가 있는 개별 A6 PDF / PNG, 전체 테이블 A4 4장 배치 PDF |
| 설정 | 점주·직원 권한, 매장명·로고·색상, 영업일 시작 시각, 주문 접수 설정, 선택적 방문 입장코드 |

매장 포인트 컬러를 저장하면 관리자·손님 화면의 버튼, 선택 상태, 연한 배경, 아이콘, 차트, 팝업과 QR 카드에 같은 계열의 팔레트가 적용됩니다. 설정 화면에서 저장 전 색상을 미리 볼 수 있고, 밝은 색의 버튼에는 읽기 쉬운 글자색을 자동으로 적용합니다.

손님 화면은 상단에 매장명과 테이블 번호를 표시하고 곧바로 카테고리·검색·메뉴 목록으로 이어집니다. 장식 배너는 없으며, 매장 로고는 인쇄용 QR 카드에 사용합니다.

테이블 이동은 방문과 기존 손님의 권한을 유지합니다. 인쇄 QR 자체는 원래 테이블에 남습니다. 다음 팀에는 새 방문을 열어 주세요. 간편 모드의 고정 QR은 URL 소유자의 물리적 현장 방문을 증명하지 않으므로, 필요하면 방문별 입장코드를 켭니다.

## 배포와 복구

```sh
sudo ./ops status
sudo ./ops backup
sudo ./ops deploy
sudo ./ops restore /opt/ongi/backups/백업이름 rehearsal-01
```

`deploy`는 백업 → 추가적 마이그레이션 → 새 API 준비 확인 → Caddy 전환 → 기존 요청 배출 순서입니다. 기존 해시 정적 파일을 보존합니다. `restore`는 **별도 DB·사진 볼륨**을 만들며 운영 데이터를 덮어쓰지 않습니다.

백업 시간은 매일 한국시간 05:00 이후 최대 5분 내, 로컬 완료 백업 보존 기간은 14일입니다. **원격 저장소 설정 전에는 호스트 상실에 대비한 백업이 아닙니다.** 원격 복사, 실제 운영 전환, 장애 대응은 [운영 가이드](docs/operations.md)를 따릅니다.

단일 서버 기본 구성은 DB·서버·전원 장애까지 무중단으로 만들지 않습니다. 수신 단말 단절, API 프로세스 재시작, 서버 전체 장애를 구분합니다. 영업 중 손님이 서비스에 접근할 수 있는 공개 서버와 매장의 보조 인터넷 회선을 검토하세요. 다중 호스트·관리형 HA DB·지속 WAL 백업은 별도 인프라 작업입니다.

## 개발 구조와 검증

```text
apps/admin       Solid 직원 앱
apps/customer    Solid 손님 앱
apps/api         Elysia 인증·주문·정산·SSE·이미지·QR
packages/db      PostgreSQL 스키마와 마이그레이션
packages/contracts  Zod 입력 계약·상태·금액 규칙
packages/ui      공통 디자인과 연결 복구
infra            Caddyfile·Podman Quadlet·백업 timer
tests            실제 DB 동시성·프로세스 종료 복구·계약 검증
```

```sh
bun run test:db             # 별도 *_test DB 준비; 개발 DB 유지
bun run check              # Biome + 타입 + 단위/DB 통합 테스트 + 두 앱 빌드
bun scripts/load.ts --seconds 600 --rate 20
```

부하 도구는 localhost PostgreSQL에 `ongi_load_*`라는 **새 DB**를 생성합니다. 검증 DB는 근거 확인을 위해 남기며, 운영 DB를 초기화하지 않습니다. 520개의 SSE와 HTTP 요청을 쓰는 도구이며 실제 브라우저 520개가 아닙니다. `BUN_CONFIG_MAX_HTTP_REQUESTS=2048`을 지정해 실행하세요. 장시간 시험은 `--seconds 28800`까지 지원합니다.

실행한 검증과 아직 실측하지 않은 환경은 [검증 보고서](docs/verification.md)에 기록합니다. 제품 정책은 [제품 명세](docs/product-spec.md), 장애 시나리오·성능 목표는 [구현 계획](docs/implementation-plan.md)을 참고하세요.

한국어 폰트는 Noto Sans KR이며 라이선스는 `assets/fonts/OFL.txt`에 있습니다. 외부 CDN이나 폰트 요청 없이 두 앱을 제공합니다.
