# 온기 운영 가이드

## 설치 파일과 데이터

기본 설치 루트는 `/opt/ongi`입니다. 다른 경로를 사용하려면 모든 명령에 `sudo env ONGI_HOME=/원하는/절대경로 ./ops ...`를 사용하세요. 자동 백업 서비스에는 설치 시 이 경로가 고정됩니다.

| 위치 | 내용 |
| --- | --- |
| `secrets/app.env`, `secrets/db.env` | 앱·DB 비밀값, 소유자만 읽기 가능 |
| `secrets/first-login.txt` | 최초 로그인 안내. 비밀번호를 바꿔도 이 파일은 초기값이므로 보관에 주의 |
| `web/releases/`, `web/current` | 릴리스별 정적 앱과 현재 릴리스 링크 |
| `web/shared/` | 이미 열린 브라우저를 위한 예전 해시 파일 |
| `caddy/`, `active-release` | 현재 라우팅과 앱 릴리스 |
| `backups/`, `last-backup`, `last-remote-backup` | 완료 백업과 마지막 성공 시각 |
| `restores/` | 별도 복원 환경과 전환 전 설정 사본 |
| `/etc/containers/systemd/ongi-*` | Podman Quadlet. systemd가 실제 서비스를 생성 |
| Podman 볼륨 | `ongi-db`, `ongi-uploads`, `ongi-caddy-data`, `ongi-caddy-config` |

운영 전환으로 복원 볼륨을 선택하면 `database-volume`, `uploads-volume` 파일에 기록합니다. 이후 `setup`, `deploy`, `backup`도 그 선택을 유지합니다. 컨테이너를 삭제해도 볼륨은 보존합니다. `podman volume prune`이나 설치 경로 일괄 삭제를 일상 운영 명령으로 사용하지 마세요.

## 영업 전 확인

매장 주소와 테이블 번호를 확인하고 QR PDF를 실제 크기로 출력합니다. A4는 4개 카드가 한 장에 배치됩니다. 실제 사용할 휴대폰으로 인쇄물을 스캔하고, 실제 사용할 태블릿에서 소리와 화면 잠금 설정을 확인합니다. 소리만으로 주문 존재를 판단하지 말고 미확인 주문 목록을 함께 사용하세요.

점주는 메뉴·품절·테이블·계정을 관리합니다. 직원 계정은 테이블·주문·정상 수납 기록을 수행하며 메뉴·통계·계정·정산 정정을 변경하지 못합니다. 퇴사 직원은 비활성화합니다. 계정 변경 시 기존 로그인 세션을 만료시킵니다.

기본 모드는 직원이 **손님 받기**를 누르면 해당 방문에 손님이 QR로 참여합니다. 이 동작은 착석을 구분하기 위한 것이며 수신 단말이 계속 접속해 있어야 한다는 뜻이 아닙니다. 이후 모든 수신 화면이 닫혀도 서버는 주문을 받습니다.

## 상태 확인과 진단

```sh
sudo ./ops status
sudo journalctl -u ongi-db.service -n 100 --no-pager
sudo journalctl -u ongi-caddy.service -n 100 --no-pager
sudo journalctl -u 'ongi-api@*.service' --since '15 minutes ago' --no-pager
sudo systemctl list-timers ongi-backup.timer
```

`status`는 서비스 상태, DB 크기·연결 수·활성 방문·미확인 주문·가장 오래된 대기 시각·변경 번호, 디스크 공간, 최근 로컬·원격 백업을 표시합니다. 컨테이너 로그 파일은 각각 20MB로 회전합니다. API 변경 요청과 느린 요청에는 `requestId`, 경로, 상태 코드, 처리 시간을 JSON으로 기록하며 비밀번호·쿠키·주문 본문·QR 토큰은 기록하지 않습니다.

`GET /api/health/live`는 프로세스 생존, `GET /api/health/ready`는 DB의 매장 설정을 읽을 수 있는지 확인합니다. 점주로 로그인한 `GET /api/admin/diagnostics`는 현재 API 프로세스의 가동 시간, 요청·서버 오류·1초 초과 요청 수, 평균 처리 시간과 RSS를 반환합니다. 프로세스 재시작 시 이 카운터는 초기화됩니다. `x-request-id` 응답 헤더로 장애 요청과 로그를 연결합니다.

외부 모니터가 있다면 준비 상태, HTTP 5xx 비율, 응답 지연, 디스크 80%/90%, 백업 실패·지연을 연결하세요. 이 레포가 외부 알림 계정이나 24시간 담당자를 자동 생성하지는 않습니다. 디스크가 부족할 때 주문·사진·백업 볼륨을 임의 삭제하지 말고 공간 증설과 검증된 오래된 백업 정리부터 진행합니다.

## 주문 연결 문제

| 상황 | 직원 행동과 시스템 동작 |
| --- | --- |
| 직원 태블릿 연결 끊김, 손님 LTE 정상 | 주문은 서버에 저장. 다른 기기로 로그인하거나 재연결하면 현재 미확인·미서빙 전체 복구 |
| SSE만 끊김 | 간격을 분산한 HTTP 조회로 계속 갱신. 읽기·쓰기 API가 정상인 경우 업무 계속 가능 |
| 손님 주문 응답 유실 | 같은 요청 번호로 저장 결과 조회·재시도. 결과 확인 중일 때 새 주문을 대신 추가하지 않음 |
| 방문 권한까지 만료된 결과 확인 중 주문 | 손님이 표시된 주문 시각·메뉴·확인 번호를 직원에게 보여주고 내역과 대조 |
| 직원 명령 응답 유실 | 원래 요청 번호로 자동 재시도. 같은 명령을 다시 만들지 않고 완료된 입력창 자동 닫기 |
| API 프로세스 종료 | systemd 재시작, DB의 주문과 변경 기록 유지. 브라우저는 재연결·최신 상태 조회 |
| DB 또는 서버 전체 장애 | 성공을 표시하지 않음. 마지막 장바구니·요청 보존. 서버 복구 또는 아래 백업 복원 |

장애 동안 받은 종이 주문은 **주문 추가 → 이전에 받은 종이 주문 기록**에서 실제 시각(최근 7일)과 사유를 선택합니다. 먼저 같은 테이블의 기존 주문·시간을 대조하세요. 비슷한 주문을 시스템이 임의로 합치지 않습니다.

## 백업과 원격 복사

`sudo ./ops backup`은 일관된 PostgreSQL 스냅샷 덤프를 만든 뒤 사진을 묶고, manifest와 SHA256을 저장합니다. 메뉴를 지우거나 사진을 교체해도 예전 사진 파일은 바로 삭제하지 않아 백업의 참조를 보존합니다.

매일 Asia/Seoul 05:00부터 최대 5분 내 자동 실행합니다. 완료된 로컬 백업은 14일 후 정리합니다. 실패한 작업은 `.partial-*`에 남으므로 원인을 확인한 뒤 해당 실패 디렉터리만 정리하세요. 대용량 사진과 과거 정적 파일은 자동 삭제하지 않으므로 저장 공간을 관찰해야 합니다.

다른 서버에 SSH 키 인증과 대상 경로를 준비합니다. **백업 수신 경로는 운영 데이터·개인 파일과 분리**하세요. 서버의 root 계정에서 알려진 호스트 키를 직접 검증하고 저장한 뒤 다음처럼 설정합니다.

```sh
sudo install -m 600 /dev/null /opt/ongi/secrets/backup-target
sudoedit /opt/ongi/secrets/backup-target
```

파일에는 한 줄로 `backupuser@backup.example.com:/srv/ongi-backups`를 넣습니다. 원격 SSH·rsync 설치와 경로 권한은 해당 서버에서 준비해야 합니다. 복사 명령은 비대화형 인증과 기존 known_hosts를 요구하며 호스트 키 검사를 끄지 않습니다.

```sh
sudo ./ops backup
sudo ./ops status
```

원격 성공 기록이 갱신됐는지 확인하고 수신 서버에서도 SHA256 검사를 실행합니다. 원격 파일은 수신자의 보존 정책으로 관리하며 이 도구가 원격 파일을 자동 삭제하지 않습니다. DB 비밀번호·도메인 설정·배포 이미지도 별도 안전한 저장소에 보관하세요. 백업 파일에는 방문·주문·계정 해시가 포함되므로 접근을 제한합니다.

데이터 손실 가능 구간은 **마지막 정상 복원 가능한 백업이 시작된 시점 이후**입니다. 하루 한 번 백업은 정상 실행 때도 하루 가까운 차이가 날 수 있고, 실패가 누적되면 더 커집니다. 기본 구성에는 WAL 연속 보관/PITR이 없습니다. 더 짧은 복원 시점이나 호스트 장애 자동 전환은 검증된 관리형 PostgreSQL/백업 시스템과 별도로 구성하세요.

## 별도 환경 복원과 실제 전환

```sh
sudo ./ops restore /opt/ongi/backups/20260909T110832Z rehearsal-01
```

예시 경로를 실제 완료 백업으로 바꿉니다. 같은 이름이 이미 있으면 거부합니다. 체크섬을 확인한 뒤 `ongi-restore-rehearsal-01` DB 컨테이너(외부 네트워크 없음)와 별도 DB·사진 볼륨을 만듭니다. 주문 건수, 방문 수, 주문 금액, 유효 수납 합계는 `restores/rehearsal-01/verification.txt`에 저장합니다.

사진 참조도 검사합니다.

```sh
sudo podman exec ongi-restore-rehearsal-01 psql -U table_order -d table_order \
  -c "SELECT image FROM menus WHERE image <> '';"
sudo podman run --rm --user 1000:1000 --network none \
  -v ongi-restore-rehearsal-01-uploads:/photos:ro \
  docker.io/library/postgres:17.11-alpine find /photos -type f
```

명령 결과를 주문·정산 원장과 대조하고 사진 파일의 SHA256·가독성을 확인합니다. **여기까지 운영에는 영향이 없습니다.** 실제 전환은 영업 중단 또는 장애 대응 시간에 실행합니다. 백업 시점 이후의 주문을 운영 조회에서 제외하므로 직원에게 대조·사후 입력할 범위를 전달해야 합니다.

```sh
sudo ./ops activate-restore rehearsal-01 --accept-backup-data
sudo ./ops status
```

이 명령은 현재 DB가 살아 있으면 먼저 백업하고 Caddy·API·DB를 멈춥니다. 원래 비밀값과 볼륨 선택을 `restores/rehearsal-01/before-activation-*`에 보존한 후 복원 볼륨·DB 비밀번호로 전환합니다. 마이그레이션과 API 준비 검사 후 Caddy를 다시 시작합니다. **원래 DB·사진 볼륨을 삭제하지 않습니다.** 전환 동안 접속 중단이 있으며, 과거 백업 복원을 무중단 업데이트처럼 취급하지 않습니다.

전환 실패 시 Caddy를 멈춘 상태로 원인을 먼저 확인합니다. 원본 DB가 정상이고 원래 상태로 돌아가기로 결정했다면, 출력된 `before-activation-*` 디렉터리의 `app.env`·`db.env`를 `secrets/`에, `database-volume`·`uploads-volume`을 설치 루트에 복구한 뒤 레포에서 `sudo ./ops setup 기존도메인`으로 재구성합니다. 원본 볼륨이 그대로 있어야 합니다. 백업 전환 후 새 주문이 이미 생겼다면 양쪽 주문을 먼저 대조하고 전환 방향을 결정해야 합니다.

호스트 상실 뒤 새 서버에서는 레포와 원격 백업을 복구하고 같은 도메인으로 `setup`을 실행한 뒤 위의 별도 복원·검증·전환을 수행합니다. 공개 주문 주소를 바꾸면 인쇄 QR도 바뀝니다. 이미 운영 데이터가 있다면 백업 복원으로 무심코 되돌리지 마세요.

## 업데이트

```sh
sudo ./ops backup
# 검토한 새 코드를 레포에 반영
sudo ./ops deploy
```

배포는 같은 서버에 새 API를 띄우고 준비 상태를 확인한 뒤 Caddy를 reload합니다. 기존 API는 35초 동안 요청을 마무리한 후 종료합니다. 이벤트 스트림은 다시 연결되고 DB 현재 상태로 복구합니다. 페이지 강제 새로고침과 장바구니 자동 제출은 하지 않습니다.

DB 마이그레이션은 잠금을 사용하고, 현재 제공된 변경은 이전 앱도 읽을 수 있는 추가적 변경입니다. 향후 컬럼 삭제·대형 변환은 한 번의 영업 중 배포에 넣지 말고 별도 단계로 검토하세요. 앱 롤백은 이전 이미지를 이용한 새 배포이며 DB 백업 덮어쓰기가 아닙니다.

```sh
sudo env ONGI_IMAGE=localhost/ongi-api:이전릴리스 ./ops deploy
```

버전 호환성을 먼저 확인한 뒤 실행합니다. 임의로 오래된 앱을 최신 DB에 연결하지 마세요. 이미지·정적 파일은 자동으로 대량 삭제하지 않습니다. 더 이상 열린 브라우저가 없는 충분한 기간이 지난 릴리스만 별도로 정리하세요.

## 실제 결제·집계 규칙

- 원 단위 정수, 주문 당시 이름·가격·분류를 보존합니다. 현재 메뉴 가격으로 과거 매출을 다시 계산하지 않습니다.
- 판매/취소 수량과 주문 금액은 해당 주문의 **실제 주문 시각** 기준입니다. 나중의 취소도 그 주문의 집계에 반영되므로 과거 주문 금액은 정정될 수 있습니다. 변경 시각은 활동 이력에 남습니다.
- 수납액은 수납 기록 시각, 수납 정정 차감은 정정 시각 기준입니다. 순수납은 해당 기간 기록 합계에서 해당 기간 정정 합계를 뺍니다. 수납 정정은 실제 카드 취소·환불을 수행하지 않습니다.
- 영업일은 한국시간의 설정된 시작 시각부터 다음 날 같은 시각 직전까지입니다. 방문 시간대는 한국시간입니다.
- 방문 팀은 방문 시작 기준입니다. 인원 미입력은 미입력 팀으로 따로 집계합니다. 0명으로 채우지 않습니다.
- 기간은 최대 93일, 수납·방문 목록은 100건씩 이동합니다. 요약 금액은 현재 페이지가 아닌 조회 기간 전체입니다.
