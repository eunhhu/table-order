# 안정성 및 실행 계획

작성일: 2026-09-09

상태: 사용자 승인 후 구현에 사용한 계획과 검증 목표. 제품 범위는 [제품 명세](product-spec.md)를 따른다. 실제 측정 결과·수행 범위는 [검증 보고서](verification.md)에 기록한다. 이 문서의 성능·복구 수치는 목표이며 측정 결과가 아니다.

## 1. 안정성의 기준

1. 저장 완료를 확인한 주문은 앱 재시작이나 알림 연결 단절로 사라지지 않는다. 이는 DB·스토리지가 정상인 장애 범위의 요구사항이다.
2. 주문 결과가 불명확하면 동일 요청의 결과를 확인한다. 성공·실패를 추측해서 새 주문을 만들지 않는다.
3. 직원에게 마지막으로 확인한 상태와 연결 상태를 보여준다. 오래된 금액·미서빙 수량을 최신 상태처럼 표시하지 않는다.
4. 주문·취소·정산을 한 데이터베이스의 트랜잭션으로 관리하고 동시 변경의 결과를 검증한다.
5. 알림·이미지·통계의 오류가 저장된 주문을 지우거나 정산 결과를 바꾸지 않는다.
6. 수신 단말이 0대여도 서버는 주문을 받는다. 수신 여부는 접수 성공과 독립적이며, 단말은 재연결 시 미수신 변경과 미처리 주문을 자동 backfill한다.
7. 시스템 장애를 완전히 없앤다는 약속 대신 장애 범위별 복구 방식·시간·데이터 손실 한계를 명시한다.
8. 일반 영업 작업은 필수 키보드 입력 0회를 목표로 한다. 단순 화면의 뒤에서 트랜잭션·중복 방지·연결 복구가 동작해야 하며, 직원이 모든 기술 상태를 수동 관리하게 하지 않는다.

## 2. 애플리케이션 구조

- Bun workspaces: apps/admin, apps/customer, apps/api, packages/ui, packages/contracts, packages/db.
- 프런트: SolidJS + Vite + TypeScript + Tailwind. Biome와 타입 검사를 공통 품질 검사에 포함한다.
- 서버: Elysia 모듈 하나 안에서 인증, 메뉴, 방문·주문, 정산, 알림, 통계를 분리한다. 주문 핵심 흐름을 여러 서비스에 분산하지 않는다.
- 저장: PostgreSQL + Drizzle. 금액·수량·활성 방문·요청 중복·정산 중복 제약을 DB에도 둔다.
- 두 프런트 앱은 각각 빌드한다. Caddy가 관리자·손님 경로와 API를 같은 도메인으로 연결한다.
- API 인스턴스의 메모리를 방문, 로그인 세션, 주문, 미확인 알림의 원본으로 사용하지 않는다. 재시작과 여러 인스턴스 사용을 고려한다.
- 서버 시간과 DB 상태를 기준으로 영업일·정산 시각을 판단한다. 단말의 마지막 연결 시각은 진단용으로만 사용하고 주문 허용 판단에 사용하지 않는다.

### 주문 제출과 중복 방지

- 클라이언트는 제출 전에 요청 식별자와 원본 요청을 보존한다. 동일 제출의 네트워크 재시도는 같은 식별자를 사용한다.
- 요청 식별자의 범위, 정규화한 요청 내용, 완료 결과를 DB에 기록한다. 같은 키와 다른 내용은 거부한다.
- 서버는 방문 권한·상태, 매장 접수 상태, 메뉴·단가·품절을 확인하고 주문·항목·활동 이력·이벤트를 하나의 트랜잭션에 저장한다.
- DB 커밋 후에만 성공과 주문 번호를 반환한다. 커밋 후 응답이 사라진 경우에도 같은 키로 원 결과를 확인할 수 있게 한다.
- 요청 조회 API는 주문 제출과 동일한 방문 권한을 요구한다. 식별자를 안다는 이유만으로 주문 정보를 반환하지 않는다.
- 결과 기록은 적어도 활성 방문과 허용된 재시도 기간 동안 유지한다. 정리 작업으로 아직 재시도 가능한 요청의 중복 방지 기록을 지우지 않는다.
- 프록시가 모든 변경 요청을 무조건 재전송하는 설정을 사용하지 않는다. 앱에서 명시한 재시도 정책과 DB 중복 방지를 적용한다.
- 동일 내용의 서로 다른 정상 주문을 자동으로 합치지 않는다.

### 동시 조작과 정산

- 주문·취소·이동·방문 종료·정산은 관련 방문과 테이블을 일관된 순서로 잠그거나 버전 조건으로 갱신한다.
- 직원 화면에서 확인한 버전보다 주문이 바뀌면 정산을 중단하고 변경분을 보여준다. 서버의 최신 총액을 확인 없이 기록하지 않는다.
- 동시 서빙·취소에서 잔여 수량을 초과하는 변경을 거부한다. 이미 완료한 동일 작업은 성공 결과를 다시 반환할 수 있게 한다.
- 외부 결제는 수행하지 않는다. 중복 클릭으로 수납 기록이 중복 생성되지 않게 한다.
- SQL 트랜잭션 안에서 파일 변환·네트워크 호출·알림 전송을 기다리지 않는다.

### 실시간 표시와 누락 복구

- 브라우저 전달은 SSE, 변경 명령은 HTTP를 사용한다.
- 주문과 이벤트를 DB에 함께 기록하고, DB의 이벤트·미확인 업무를 기준으로 전송한다. 전달은 중복 가능성을 허용하고 수신 쪽에서 중복을 제거한다.
- 주문 API는 온라인 단말 수, SSE 구독자 수, heartbeat, 전달 작업 성공 여부와 무관하게 저장·응답한다. 별도의 관리자 로그인이나 수신 확인을 주문 커밋 조건으로 두지 않는다.
- 영속 이벤트를 읽는 전송 작업은 앱이 재시작되어도 미전송 작업을 다시 찾을 수 있게 한다.
- PostgreSQL LISTEN/NOTIFY를 사용한다면 갱신을 빠르게 알려주는 보조 신호로만 사용한다. 주문 커밋 성공이 NOTIFY 전송 성공에 의존하지 않게 하고, 신호 누락은 DB 조회로 복구한다.
- SSE 재연결, 브라우저 복귀, 일정 주기마다 권한 범위의 현재 상태·미확인 주문을 DB에서 대조한다. 만료된 이벤트 커서는 전체 현재 상태로 복구한다.
- 단말별 수신 커서와 업무 확인 상태를 분리한다. 커서가 없는 새 단말도 현재 미확인·미처리 주문 전체를 읽고 실시간 전달을 시작할 수 있어야 한다.
- backfill은 자동으로 수행하고 페이지별 중단 지점에서 안전하게 재개한다. backfill 중 들어온 신규 이벤트를 버퍼링·병합하거나 일관된 경계부터 다시 읽어, 현재 상태 조회와 실시간 구독 사이에 빈 구간이 없게 한다.
- 단말은 엔터티 식별자와 상태 버전을 기준으로 적용하며 중복·오래된 이벤트로 최신 상태를 되돌리지 않는다. 취소·서빙·이동·정산·방문 종료도 복구 범위다.
- 과거 이벤트 보존 기간이 지났어도 미확인 업무는 DB에서 다시 구성한다. 알림 전송 기록을 정리한다고 미확인 주문까지 지우지 않는다.
- 재접속 시 미확인 주문 수를 묶어서 알리고, 처리할 일이 남은 주문부터 표시한다. 과거 알림 소리를 대량 재생하지 않는다. 수신 재개 버튼을 요구하지 않는다.
- DB 시퀀스 번호가 커밋 순서를 보장한다고 가정하지 않는다. 이벤트 전송 커서 설계와 스냅샷 대조에서 늦게 커밋한 항목의 누락을 시험한다.
- 여러 인스턴스와 여러 직원 단말이 있더라도 한 단말로 전달했다고 업무를 처리 완료로 바꾸지 않는다. 직원의 명시적 접수·서빙 기록이 별도로 필요하다.
- SSE 실패 시 간격에 무작위 분산과 상한을 둔 HTTP 재조회로 전환한다. 모든 손님이 동시에 재연결하는 부하를 제한한다.
- 연결 정상 / 재연결 중 / 최신 상태 확인 불가와 마지막 동기화 시각을 표시한다. API 통신이 정상인 경우 SSE 장애만으로 전체 조작을 막지 않고 명령 응답으로 상태를 확인한다.

| R26 | 서빙 완료를 잘못 누른 뒤 바로 되돌리기 | 후속 변경이 없으면 1회 조작으로 서버 정정·이력 저장. 후속 변경이 있으면 덮어쓰지 않음 |
| R27 | 인원 입력 없이 손님 받고 정산 | 정상 진행 가능. 인원 미입력을 0명 또는 임의 인원으로 집계하지 않음 |
| R28 | 모든 일반 작업을 터치만으로 수행 | hover·우클릭·드래그 필수 동작 없음. 주요 버튼 크기·간격·한글 레이블과 실제 태블릿 오조작 확인 |
| R29 | 모든 직원 단말을 종료한 상태에서 100건 주문 | 서버가 독립 주문 100건 저장·고객에게 정상 결과 반환. 다시 연결한 단말에서 100건의 최신 상태 확인, 중복·누락 0건 |
| R30 | 단말 backfill 중 신규 주문·타 단말의 서빙·취소 발생 | 복구와 실시간 전환 후 DB의 최신 상태와 일치. 처리한 주문 부활·새 주문 누락 0건 |
| R31 | 수신 커서 없는 새 기기 또는 이벤트 보존 기간보다 늦게 재접속 | 현재 미확인·미처리 업무를 DB에서 자동 복구. 미확인 목록을 빈 화면으로 오인하지 않음 |
| R32 | backfill 도중 여러 번 연결이 끊기고 API도 재시작 | API 복구 후 같은 요청의 재시도와 backfill 재개·중복 제거로 상태가 수렴. backfill 자체는 신규 접수를 막지 않으며 과거 알림 폭주나 재개 버튼 요구 없음 |

핵심 장애·동시성 검증은 실제 PostgreSQL과 컨테이너 프로세스를 사용한다. 단위 테스트의 모의 DB 결과만으로 통과를 선언하지 않는다. 이는 소유한 개발·검증 환경의 복구 테스트이며 외부 대상에 장애나 부하를 가하지 않는다.

## 4. 성능·복구 목표

아래 수치는 큰 매장을 위한 초기 검증 목표이며 지원 한도를 확정한 수치가 아니다. 실제 하드웨어·DB·이미지·과거 데이터 크기를 고정하고 결과를 기록한다.

| 항목 | 초기 목표와 측정 조건 |
| --- | --- |
| 매장 규모 | 테이블 100개, 손님 브라우저 세션 500개, 직원 세션 20개 |
| 정상 부하 | 위 연결을 유지하고 초당 주문 제출 20건을 60분 수행 |
| 순간 부하 | 초당 주문 제출 50건을 60초 수행하고 대기·오류·회복 상태 측정 |
| 주문 응답 | 정상 검증 환경에서 서버 응답 p95 1초 이내. 인터넷 구간 지연은 별도 기록 |
| 실시간 화면 | 정상 통신에서 저장→직원 표시 p95 2초 이내, SSE 대체 조회 시 10초 이내 목표 |
| 장시간 실행 | 8시간 실제 업무 혼합 부하. 메모리·연결·미전송 이벤트가 계속 누적되지 않아야 함 |
| 데이터 정확성 | 승인된 주문 유실·동일 요청 중복·금액 불일치 0건 |
| API 프로세스 장애 | DB·호스트 정상 조건에서 30초 이내 재기동·준비 상태 회복 목표. 접속 장애 화면은 즉시 안내 |
| 복원 | 기준 데이터셋으로 실제 복원 시간을 측정. 별도 저장소가 없는 상태를 재해 복구 완료로 표시하지 않음 |

- 부하 도구는 Bun 기반 제출·연결 시나리오와 Playwright 업무 시나리오를 구분한다. 실제 브라우저 500개를 실행했다는 식의 잘못된 보고를 하지 않는다.
- 주문·취소·정산 트랜잭션과 SSE DB 접근에 우선 자원을 남긴다. 통계는 기간 제한·인덱스·집계·캐시로 보호한다.
- DB 연결 수, 요청·쿼리 제한 시간, 요청 크기, 이미지 업로드 크기·변환 동시성을 제한한다. 매장 공용 IP 하나를 이유로 정상 손님 전체를 차단하는 제한 정책을 피한다.
- 정적 사진은 크기별 최적화와 캐시를 적용하고, 주문·방문·정산 응답을 공용 캐시로 제공하지 않는다.

## 5. 배포 구성과 장애 한계

### 기본 납품: 단일 Linux 서버 설치

- Caddy, API, PostgreSQL, 영속 데이터·사진·인증서 볼륨, Podman Quadlet/systemd 설정.
- Caddy가 HTTPS·정적 앱·API 라우팅·상태 검사를 담당한다.
- 프로세스 생존 검사와 DB 접근·마이그레이션 호환성을 포함한 준비 상태 검사를 구분한다. 재시작 폭주를 막는다.
- API 교체는 새 컨테이너 준비 확인 → 라우팅 전환 → 기존 요청 종료를 기다림 → 이전 컨테이너 정리 순서다. 예전 프런트가 열린 채로 새 API를 사용해도 되는 호환 기간을 둔다.
- 오래 열린 고객 페이지의 해시된 정적 파일을 배포 직후 삭제하지 않는다. 업데이트 때문에 주문 도중 강제 새로고침하지 않는다.
- 단일 서버의 API를 두 개 띄워도 서버·DB·Caddy 자체 장애까지 해결한 고가용성 구성이라고 부르지 않는다.
- 호스트 전원·디스크·DB·매장 인터넷 장애에는 중단이 남는다. 앱 자동 재시작은 하드웨어 복구가 아니다.

### 높은 가용성이 필요한 매장의 권장 확장

- 독립 호스트의 앱, 진입점 이중화, 장애 전환이 검증된 PostgreSQL 구성을 사용한다. DB 고가용성은 관리형 서비스 또는 별도 운영 가능한 검증된 구성으로 제공받는 것을 우선한다.
- 다중 호스트에서는 사진을 단일 호스트 볼륨에만 두지 않는다. 공유 또는 객체 저장소와 그 복구 정책이 필요하다.
- 복제는 백업의 대체가 아니다. 동기·비동기 복제의 장애 전환 시 손실·지연 차이를 명시한다.
- 별도 서버·DB 서비스·원격 백업 저장소·네트워크 장비는 레포 실행만으로 확보할 수 없다. 비용이 드는 자원을 임의 생성하지 않는다.
- 매장 인터넷 단절에도 디지털 주문을 계속 받아야 한다면 LTE/5G 보조 회선이나 매장 내부 서버가 필요하다. 로컬과 클라우드의 자동 양방향 주문 동기화는 별도 설계이며 기본 범위에 슬쩍 추가하지 않는다.
- 고가용성 배포와 네트워크 장애 전환은 해당 인프라가 제공된 환경에서 별도 실측해야 한다. 단일 호스트 테스트 결과로 무중단을 주장하지 않는다.

### 설치·백업·업데이트 산출물

- .env.example, Containerfile, Caddyfile, Quadlet, setup/deploy/status/backup/restore 명령과 운영 README.
- 의존성·이미지 버전 고정, 설치 환경 사전 검사, 비밀값 생성, DB 마이그레이션 잠금, 첫 관리자 설정, 데모 데이터 선택 설치.
- 재실행해도 기존 DB·사진·계정을 초기화하지 않는다. 운영 데이터 초기화는 배포 명령에 포함하지 않는다.
- 자동 백업과 보존·용량 관리, 실패 상태 표시, 원격 저장소 연결 설정을 제공한다. DB 덤프와 사진의 참조 일관성을 고려한다.
- 운영 권장안은 일일 기준 백업과 지속 WAL 보관으로 복원 지점을 줄이는 것이다. 원격 저장소가 없으면 호스트 상실에 대비하지 못한다는 상태를 표시한다.
- 실제 데이터 손실 가능 구간은 마지막으로 복구 가능한 백업/WAL 시점으로 계산해 표시한다. DB가 남아 있는 API 재시작과 호스트 전체 상실의 복구 보장을 구분한다.
- 보존 기간 내 사진을 먼저 삭제해 복원된 DB가 없는 파일을 가리키지 않도록 삭제 정책과 백업을 함께 설계한다.
- DB 변경은 기존·새 앱이 함께 동작하는 추가적 변경부터 적용한다. 컬럼 제거·대형 변환은 별도 배포 단계로 분리한다.
- 앱 버전 복귀와 DB 복원을 구분한다. 오래된 DB 백업을 덮어쓰면 이후 주문을 잃을 수 있으므로 자동 앱 롤백에 DB 덮어쓰기를 포함하지 않는다.
- 요청 식별자를 포함한 구조화 로그, 로그 회전, 오류율·지연·DB 연결·디스크·미확인 주문·이벤트 대기·백업 상태를 확인할 수 있는 운영 정보를 제공한다.

## 6. 구현 단계와 완료 조건

| 단계 | 구현 범위 | 완료 조건 |
| --- | --- | --- |
| 1. 계약·기반 | 스키마, 권한·세션, 상태 전이, 요청 중복 방지, 모노레포·검사 도구 | 데이터 불변 규칙과 API 계약 확정, 실제 DB의 동시 요청 검증 |
| 2. 주문 흐름 | 메뉴 CRUD, 착석·참여, 장바구니, 제출·내역, 직원 주문·수신 | 손님→서버→직원 흐름과 R01~R05, R09~R11 통과 |
| 3. 매장 운영 | 구역·테이블 현황, 확인·서빙 기본 모드와 선택적 세부 조리, 직원 추가·취소, 이동·정산과 자동 테이블 비움 | 수량·금액 검증, R06~R08·R20~R22·R24~R28 통과 |

| 5. 관리 기능 | QR PDF·PNG, 통계, 메뉴·매장 설정, 계정 관리 | 출력물 스캔, 과거 가격·취소·정산 정정 집계 검증 |
| 6. 운영 검증 | Podman·Caddy, 백업·복원, 배포 전환, 부하·장시간 시험 | 깨끗한 Linux 환경 설치, 재부팅·복원·업데이트 시나리오와 결과 문서 |

- 안정성의 기반인 중복 방지·트랜잭션·영속 이벤트는 1~2단계부터 구현한다. 4단계는 이를 실제 실패 상황에서 보강하는 단계다.
- 순서를 나누는 것은 구현·검증 단위이며 기능을 임시 화면이나 데모로 대체한다는 의미가 아니다.
- Bun 테스트, 실제 PostgreSQL 통합 테스트, Playwright 업무 테스트, 컨테이너 장애·부하 검증을 변경 위험에 맞게 사용한다.
- 린트·타입·빌드·중요 시나리오가 통과해야 납품 가능하다. 실행하지 못한 장비·인프라 검증은 통과로 쓰지 않는다.
- 성능 보고서에는 환경·데이터 크기·동시 연결·처리량·p95·실패율·장애 복구 시간과 제한을 기록한다.
- UX 검증에는 태블릿 기준 업무별 터치 횟수, 필수 타이핑 여부, 불필요한 모달, 되돌아가기, 새 주문 갱신 중 오조작을 기록한다. 기능이 존재하는 것만으로 현장 사용성 검증을 통과했다고 보고하지 않는다.

## 7. 확인한 기술 자료

- [Elysia SSE](https://elysiajs.com/essential/handler): 실시간 전달 구현 참고.
- [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html): 전달 시점·세션·큐 동작을 검토하고 영속 업무 저장과 분리하는 설계 근거.
- [PostgreSQL 고가용성](https://www.postgresql.org/docs/current/high-availability.html): 복제·장애 전환과 동기/비동기 방식의 손실·지연 차이.
- [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy): upstream 상태 검사·라우팅·재시도·스트리밍 설정 참고.
- [Podman Quadlet](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html): systemd 관리·부팅·종료·상태 검사 설정 참고.

이 문서의 제품 정책과 수치는 해당 자료의 보장 내용이 아니라 이 프로젝트의 설계 및 검증 목표다.
