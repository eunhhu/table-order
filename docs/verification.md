# 구현 및 운영 검증

검증일: 2026-09-09. 모든 주문·수납 데이터는 소유한 로컬 검증 환경의 시험 데이터이며 실제 결제를 실행하지 않았다.

직원 단말 없이 주문을 저장하고, 응답 유실·API 종료·재접속 후 원 주문과 현재 업무 상태를 복구하는 흐름을 실제 PostgreSQL과 브라우저에서 확인했다. 설치·배포·백업·복원·부팅 자동 실행도 Linux VM에서 실행했다. 아래 결과는 해당 조건의 관측값이며 모든 매장의 무중단 운영이나 지원 규모를 보장하는 수치가 아니다.

## 환경과 최종 검사

| 항목 | 실제 사용 환경 / 결과 |
| --- | --- |
| 개발 | macOS ARM64, Bun 1.4.0, PostgreSQL 17.6 컨테이너의 기존 개발 볼륨 |
| 배포·부하 | Fedora 43 ARM64 VM, 4 vCPU / RAM 8GB, Podman 5.8, PostgreSQL 17.11, Bun 1.4.0 |
| 프록시 | Caddy 2.11.4, 로컬 시험 도메인 `ongi.localhost`, HTTPS |
| 브라우저 | Playwright가 제어한 Chrome, 손님 390×844 / 관리자 1024×768 |
| 최종 검사 | 포인트 컬러 보강 후 `bun run check`: Biome, 타입 검사, 테스트 **32개 / assertion 1,627개 통과**, 두 앱 production build 성공 |
| 설치 스크립트 | `bash -n ops` 통과, 실제 rootful Quadlet 서비스 실행 |
| CI | GitHub Actions에 같은 검사와 별도 PostgreSQL 구성을 추가. 원격 Actions 실행은 하지 않음 |

서버 비밀번호·세션·개발 `.env`는 증거 파일에 포함하지 않는다. `output/`의 로컬 로그와 사진 중 필요한 비밀값 없는 결과만 [evidence](evidence/)에 보존했다.

## 주문 정확성과 복구

단위 테스트 외에는 실제 PostgreSQL을 사용한다. 테스트 도구는 별도 `*_test` DB만 초기화하며 개발 DB를 유지한다.

| 시나리오 | 확인한 결과 |
| --- | --- |
| 같은 요청 키로 동시에 12번 제출 | 주문 1건, 동일 결과 반환. 같은 키로 다른 내용은 충돌 처리 |
| 수신 단말·SSE 연결 없이 독립 주문 100건 | 모두 저장되고 총액 일치. 단말 연결이 접수 조건에 들어가지 않음 |
| 커밋 전 API 강제 종료 | 실제 자식 API 프로세스를 종료. DB 처리 중임을 확인하고 종료한 뒤 주문·항목·완료 명령이 부분 저장되지 않음. 재시작 후 같은 키로 1건 저장 |
| 커밋 후 API 강제 종료 | 재시작 후 같은 키가 기존 주문을 반환하고 새 단말에서 업무 상태를 복구 |
| 과거 이벤트 삭제·유효하지 않은 수신 커서 | DB의 현재 주문·서빙 상태로 복구. 이미 처리한 수량이 되살아나지 않음 |
| 두 직원의 서빙·부분 취소 경쟁 | 허용 수량을 넘지 않고 뒤 요청은 충돌 또는 최신 결과 처리 |
| 정산 확인 중 추가 주문·정산 동시 실행 | 오래된 금액의 정산 거부, 중복 수납 방지, 주문과 정산 합계 일치 |
| 정산했지만 음식이 남은 방문 | 남은 업무가 계속 표시되며 잘못된 방문 종료 방지 |
| 잘못 누른 서빙 되돌리기 | 시간·처리자·상태 버전 확인 후 정정. JSONB에 저장한 원 명령 결과를 통한 재시도도 검증 |
| 테이블 이동·다음 팀 착석 | 기존 방문 권한은 이동 후 유지. 종료된 이전 팀 권한으로 새 팀 주문 불가 |
| 메뉴 가격 변경·품절·삭제 | 주문 전 재확인 요구, 과거 이름·단가 보존, 메뉴 보관 처리 후에도 이력 유지 |
| 인원 미입력 | 정상 착석·정산 가능. 미상 인원을 임의의 0명으로 집계하지 않음 |
| 인증·권한 | 세션과 요청 Origin 확인, 직원 권한 제한, 마지막 점주 보호, 명령 트랜잭션 안에서 현재 직원 권한 재확인 |

SSE는 DB 변경을 알리는 신호다. 재연결 시 현재 활성 방문·미처리 업무 스냅샷과 버전을 대조하고, 연결이 실패하면 간격을 분산한 HTTP 재조회로 복구한다. 계획에 있던 페이지별 이벤트 재생 대신 현재 상태 대조를 사용한다. 단말의 수신 커서와 직원의 업무 확인은 분리되어 있으며 수신 재개 버튼은 없다.

## 실제 브라우저 업무 흐름

1. 모든 관리자 브라우저를 닫은 상태에서 손님이 11,000원 메뉴 2개를 주문했다. 프록시가 서버 응답을 받은 다음 브라우저 전달만 중단하는 방식으로 응답 유실을 만들었다. 손님 화면이 원 요청을 조회하여 주문 번호를 회복했고 DB에는 **1건 / 22,000원**만 남았다. 새로 로그인한 관리자가 자동으로 해당 주문을 받았다.
2. 관리자가 주문 확인 → 1개 부분 취소 → 남은 1개 서빙 → 되돌리기 → 다시 서빙 → 카드 정산·퇴석을 진행했다. 정산은 **11,000원**이며 손님 화면도 새로고침 없이 종료된 방문으로 바뀌었다.
3. 1024×768 화면에서 인원 없이 착석 → 직원 주문 중 응답 유실 → 자동 결과 복구 → 테이블 이동 → 확인·서빙 → 현금 정산·퇴석을 진행했다. 원 주문 1건만 저장되고 결과를 회복한 주문 창은 자동으로 닫혔다. 구역 필터는 새로고침 후 유지됐다.
4. 새 방문 입장 후 손님 메뉴가 다시 표시됐다. VM 재시작 뒤 기존 손님 페이지에서 서버 변경이 자동으로 반영되는 것도 확인했다.
5. Caddy가 제공한 빌드 결과의 관리자 화면을 열어 렌더링과 가로 넘침 여부를 확인했다. 로컬 SSH 전달 포트와 실제 Origin이 달라 이 화면 검증은 API 로그인 후 공유 쿠키를 이용했다. **공개 도메인에서의 로그인·인증서 발급을 검증한 것은 아니다.** 개발 환경의 로그인 폼과 실제 Caddy API는 별도로 확인했다.

| 자주 하는 작업 | 확인한 기본 경로 |
| --- | --- |
| 손님 받기 | 테이블 카드에서 1회. 인원 필수 입력 없음 |
| 주문 확인 / 전체 서빙 | 각각 1회 |
| 서빙 실수 정정 | 표시된 되돌리기 버튼 1회. 서버에서 정정 가능 여부 확인 |
| 정산·퇴석 | 정산 열기 → 수단별 정산·퇴석, 2회 |
| 정리 완료 | 1회 |
| 부분 취소·이동 | 항목·수량·사유 또는 목적지 버튼으로 선택. 기본 경로에 필수 키보드 입력 없음 |

주요 테이블 버튼은 실제 DOM에서 높이 **48px**를 측정했다. 1024px 관리자와 390px 손님 화면에서 문서 가로 넘침이 없었다. 실제 손가락 터치·주방 조명·장갑·기기 절전·알림음 청취 시험을 대신하는 결과는 아니다.

제출한 요청 키·결과 확인은 유지하고, 손님 장바구니는 로컬에 보존한다. 관리자 구역 필터와 제출한 명령 복구 정보를 보존한다. **아직 제출하지 않은 모든 관리자 편집 폼을 브라우저 전체 새로고침 후 복원하는 기능까지 제공하지는 않는다.**

화면 증거: [관리자 태블릿](evidence/admin-final-tablet.png), [손님 모바일](evidence/customer-final-mobile.png), [손님 응답 유실 복구](evidence/guest-recovered-order.png), [태블릿 정산](evidence/tablet-settlement-confirmed.png). 화면 속 매출은 위 브라우저 시험에서 생성한 데이터다. 메뉴 사진이 없는 예시 메뉴는 대체 아이콘을 표시한다.

## 부하 시험

원시 결과: [Linux 600초](evidence/performance-linux-600s.json).

| 조건 / 지표 | 결과 |
| --- | --- |
| 연결 목표 | 테이블 100개, 손님 SSE 500개, 직원 SSE 20개 |
| 부하 | 초당 20건을 600초 제출, 마지막 처리·방문 재참여까지 실제 608.855초 |
| 저장 | **12,000건 / 오류 0건 / DB 12,000건 / 총 12,000,000원 일치** |
| 현재 상태 조회 | 140,899회, 실패 0회 |
| HTTP 응답 | p50 21.6ms / **p95 659.1ms** / p99 1,307.7ms |
| 제출 예정 시각 → 결과 확인 | p95 733.4ms, 도구의 전송 대기 p95 3.2ms |
| API 메모리 | 15초 간격 관측 RSS 256~477MB. 업무 주기 후 감소도 관측 |

520개는 HTTP/SSE 연결을 만드는 Bun 시험 도구의 세션이며 **520개의 실제 브라우저가 아니다.** 방문 종료·다음 팀 참여가 겹친 순간에는 연결 수가 461/467로 일시 감소했고 이후 520으로 회복했다. 단순 생성뿐 아니라 조회와 방문 교체를 포함한다. API와 DB가 같은 VM에 있고 일반 인터넷 구간을 포함하지 않는다.

추가로 macOS API + VM DB에서 초당 50건을 60초 제출하여 3,000건 모두 저장됐지만, 처리가 끝나기까지 **83.55초**, HTTP p95 **1,326.4ms**가 걸렸다. 이는 대기가 발생한 결과이므로 초당 50건을 계속 처리할 수 있다는 근거로 쓰지 않는다.

Linux 부하 시험 후 권한 재확인·준비 상태 검사·버튼 크기 등의 보강이 있었다. 이후 최종 소스에 전체 검사와 컨테이너·배포 검증을 다시 수행했다. 모든 최종 변경 뒤 동일 10분 부하를 다시 측정한 것은 아니다.

## 배포·백업·복원

시험 설치는 독립 경로 `/var/lib/ongi-verify`를 사용했다. 제품 기본 경로는 `/opt/ongi`다. 비밀값 생성, DB·사진·Caddy 볼륨, 마이그레이션, rootful Quadlet, 정적 파일, HTTPS 프록시를 실제 구성했다. Linux 컨테이너 API 검사는 사진 업로드·조회와 QR PDF를 포함해 12개 항목을 통과했다.

| 시험 | 관측 결과 |
| --- | --- |
| 실제 주문 중 API 배포 전환 | 겹치는 구간에 주문 **126건**, HTTP 오류 **0건**. 준비 상태 조회 630회 모두 성공. SSE 2개 연결에서 sync 128회, 이전 해시 파일 2개 유지, DB와 손님 합계 126,000원 일치. [원시 결과](evidence/blue-green.json) |
| 백업 복원 | 새 DB·사진 볼륨으로 복원 **2.872초**, 복원 볼륨을 서비스에 연결하는 전환 **3.764초**. 원래 볼륨은 유지 |
| 복원 데이터 | 주문 255건, 방문 5건, 주문 합계 255,000원, 유효 수납 2,000원 동일 |
| 사진 복원 | 시험 사진 2개의 원본·복원 SHA-256 동일. 두 사진은 동일 내용의 작은 시험 이미지 |
| 일일 백업 실행 | systemd 백업 서비스 종료 코드 0, `Result=success`, timer 활성 확인 |
| Linux VM 완전 정지 후 시작 | 시작 요청부터 HTTPS 준비 완료까지 **15.142초**. DB·API·Caddy·백업 timer 자동 활성, 위 데이터 동일. [원시 결과](evidence/reboot.json) |

배포 시험은 API 준비 후 Caddy 전환, 기존 연결 종료 유예, 이전 정적 파일 보존을 포함한다. 사전 실행한 기준 부하와 혼동하지 않고 **배포와 실제로 겹친 실행**의 결과만 표에 기록했다. DB 마이그레이션 전체 종류나 모든 고부하 상황에서 무중단임을 증명하지는 않는다.

복원 기준 백업은 `20260909T120509Z`, 활성화한 볼륨은 `ongi-restore-verified-restore-db` / `ongi-restore-verified-restore-uploads`다. 사진 두 개의 SHA-256은 `2bc72b8af5ede1fd07401b98427d5f75fdb14a84cfe7a2cc24dc6ec7a0dfdbfb`였다. 위 복원 시간은 **작은 시험 데이터셋**의 실측이며 큰 매장 데이터의 복구 시간으로 사용할 수 없다.

실제 배포 시험에서 발견한 사진 볼륨 소유권 변경, SELinux의 백업 스크립트 직접 실행 거부, 종료 유예보다 짧은 컨테이너 종료 제한을 수정하고 재검증했다. 설치는 systemd 백업 서비스를 직접 실행해 성공 여부까지 확인하도록 했다.

## 통계·인쇄물

- 실제 DB에서 방문 105건·수납 104건으로 100건/4건 페이지 이동과 기간 전체 수납 합계 104,000원을 대조했다. 수납 없는 방문, 알려진 인원 104명과 인원 미상 방문 53건을 구분했다.
- 한국시간 영업일 경계 04:59:59 / 05:00:00, 다음 날 정산 정정, 과거 가격, 사후 기록의 실제 주문 시각과 입력 시각을 검증했다.
- A6 개별 PDF, A4 4개 배치 PDF와 PNG를 생성했다. PDF 렌더 결과를 확인하고 PNG의 QR을 디코더로 읽어 예상 주문 URL과 대조했다. 최종 굵은 한글 폰트가 포함된 [QR 카드 PNG](evidence/table-card.png)를 시각 검토했다. 프린터 출력물·실제 휴대폰 카메라 스캔 시험은 하지 않았다.

## 매장 포인트 컬러 보강

관리자·손님 앱과 QR 생성기가 같은 팔레트 함수를 사용하도록 수정했다. 페이지 배경·선택 상태·아이콘·차트·호버·팝업·인쇄물에 남아 있던 고정 민트색을 매장색에서 파생하는 토큰으로 교체했다. 문서 루트에 적용하여 body에 표시하는 팝업에도 상속되며, 최근 색상은 새로고침 중에도 유지한다. 설정 화면에는 저장 전 미리보기를 추가했다.

- 실제 저장된 `#850000`으로 두 앱의 전체 화면과 동일한 계열의 배경을 확인했다.
- 별도 검증 브라우저에서 서버 스냅샷의 색상만 보라·노랑으로 대체해 팝업 상속, 모바일 가로 넘침 없음, 노란 버튼의 검은 글씨, 호버와 새로고침 후 유지를 확인했다. 시험 색상을 매장 DB에 저장하지 않았다.
- 216가지 RGB 색 조합에서 기본·호버 버튼과 텍스트 대비 4.5:1 이상, 버튼 테두리 대비 3:1 이상을 검사했다. 잘못된 저장 색상은 기본값으로 복구한다.
- 현재색·보라·노랑 QR PNG 각각의 배경 픽셀을 팔레트와 대조하고 세 파일 모두 QR URL 디코딩에 성공했다. QR 자체의 흑백 영역과 여백은 유지했다.
- 저장하지 않은 설정 미리보기의 색이 전체 페이지나 실제 저장값을 바꾸지 않는 것을 확인했다. 개발 미리보기는 패키지 export 캐시를 갱신하기 위해 재시작했다.

색상 보강의 브라우저·QR 증거는 로컬 `output/playwright/theme-*.png`, `output/pdf/theme-*.png`, `output/theme-qr.json`에 있다. 앞선 운영 배포·부하 수치는 이 색상 보강 전의 측정값이다.

## 측정하지 않은 범위와 운영 전 점검

손님 화면 간소화 후에는 배너·소개 문구·서비스 로고를 제거하고 매장명을 상단으로 옮겼다. 375×812 모바일에서 첫 메뉴 시작 위치 246.4px, 배너 요소 0개, 가로 넘침 없음과 메뉴 상세·주문 내역 이동을 확인했다. 해당 변경에는 Biome·타입·두 앱 빌드를 실행했으며 주문 로직의 DB 테스트를 반복하지 않았다. 이전 배너가 있는 화면 증거는 변경 전 기록이다. 새 화면은 로컬 `output/playwright/customer-menu-first.png`에 있다.

다음 항목은 통과한 것으로 표시하지 않는다.

- 계획의 **60분 정상 부하**, **8시간 혼합 부하**, 오래 누적된 대형 매장 이력에서의 성능·메모리 안정성.
- 실제 iOS/Android 기기의 절전·백그라운드·Wi-Fi/LTE 전환, 현장 알림음과 인쇄된 QR의 카메라 인식, 바쁜 직원의 손가락 조작.
- 저장에서 실제 직원 화면 표시까지의 p95, 실제 WAN·서버 디스크 포화·호스트 강제 전원 차단 시험. API 프로세스 강제 종료와 VM 정지/시작은 수행했지만 이와 같은 장애는 아니다.
- 실제 공개 도메인·인증서 자동 발급, 원격 SSH 백업 저장소, 호스트 상실 복구, WAL 지속 보관·관리형 HA DB·다중 호스트 장애 전환.

기본 배포는 단일 서버다. 수신 단말이 없어도 **서버와 DB에 접근 가능한 손님**은 주문할 수 있다. 서버나 DB 자체가 접근 불가하면 접수 성공을 표시하지 않고 결과 확인·연결 상태를 안내한다. 매장 수신 화면이 꺼진 동안 저장된 주문은 돌아온 직원이 볼 수 있지만 사람이 실제로 조리를 시작했다고 표시하지는 않는다.

영업 전에는 사용할 Linux 서버·공개 도메인에 설치하고 원격 백업을 설정한 다음, 실제 단말과 프린터로 위 미측정 항목을 확인해야 한다. 장애 대응·데이터 손실 구간·복원 전환 명령은 [운영 가이드](operations.md)에 있다.
